# Server01 first deployment guide (Windows 10)

This is a runbook for the first production deployment of the Smart Home Kiosk and its Cast sidecar on `server01`. The user confirmed server01 runs Windows 10, the speedtester script runs on their PC, and the app, tablet, and speakers share the home LAN. The stable HTTPS name, certificate path, proxy choice, service permissions, and Cast multicast path still need first-deploy checks.

## What is confirmed in this checkout

- The app is Next.js 14.2 with `npm run build` and `npm run start` production scripts. Next.js documents self-hosting on a Node.js server; a reverse proxy is recommended in front of the app. See [Next.js self-hosting](https://nextjs.org/docs/app/guides/self-hosting) and [Next.js 14 deployment](https://nextjs.org/docs/14/app/building-your-application/deploying).
- The PWA manifest and service worker are present. The worker caches only the offline page and icons; it bypasses API requests and does not cache live data or controls. A service worker requires a secure context, normally HTTPS outside localhost; see the [W3C Service Workers specification](https://www.w3.org/TR/service-workers/).
- `services/cast-bridge` is a Python 3.10+ sidecar using the pinned PyChromecast dependency. It listens only on `127.0.0.1:8765` by default. The Next.js Cast facade calls that loopback address and accepts only loopback bridge URLs. Keep both processes on the same machine. PyChromecast discovery uses multicast DNS (mDNS) and requires the host and Cast devices to share a subnet; multicast UDP 5353 must pass the host and Wi-Fi network. See [PyChromecast networking requirements](https://github.com/home-assistant-libs/pychromecast#networking-requirements).
- `GET /api/speed-history` reads `SPEED_HISTORY_CSV_PATH` on the server, never in the browser. It returns up to 30 newest rows by default (100 maximum), rejects files over 5 MiB, and sends `Cache-Control: no-store`. The README documents the producer output as `F:\scripts\speedtester\log\speedtest-results.csv`; because the script runs on the user's PC, server01 needs a read-only UNC share or a copied snapshot.
- The current `server.cmd` is a development-era launcher: it kills matching titled windows, runs `git pull`, `npm install`, and a production build on every launch, then opens an interactive command window. Do not use it as an unattended production service. Leave it unchanged; deploy with a controlled release folder and a service supervisor instead.

## Prepare now

These steps do not depend on server01 access:

1. Record the app release/commit to deploy and retain this checkout as the source. Build the production app in a clean release folder with the Node.js version selected for this project. Do not run the development server in production.
2. On a Windows machine with Python 3.10+, create and validate a dedicated virtual environment for `services/cast-bridge`; install its pinned `requirements.txt`. Keep the bridge source and virtual environment in a stable service folder, separate from the app release folder.
3. Prepare a secret inventory. Only provision secrets for features being enabled. Existing server-side settings include `CAST_BRIDGE_TOKEN`, `CONTROL_PIN_HASH`, `CONTROL_AUTH_SECRET`, Spotify settings documented in `docs/spotify-auth.md`, Electrolux settings documented in `docs/electrolux.md`, and optional `OCTOPRINT_URL` / `OCTOPRINT_API_KEY`. `SPEED_HISTORY_CSV_PATH` and the Spotify/Electrolux token-store paths are paths, not secrets. Never add production values to source, browser variables (`NEXT_PUBLIC_*`), build logs, or this guide.
4. The user confirmed `F:\scripts\speedtester\checkNetwork.ps1` runs on their PC. Before first deploy, verify that the README's output CSV path exists there, agree on a read-only share or snapshot copy, and check whether the script can be writing the file while the app reads it.
5. List the kiosk tablets and Cast devices, the network/subnet they use, and any existing internal DNS, certificate authority, and reverse proxy. No values for these have been confirmed.

## Decisions for the first-deploy session

Agree these before opening access to kiosk clients:

- **Stable origin:** choose a stable internal DNS name that resolves to server01 from every kiosk client. Prefer an internal FQDN if available; use that exact name in the trusted certificate and Spotify callback when Spotify is enabled. Verify the origin on the tablet before installation; do not depend on a browser certificate-warning bypass.
- **HTTPS termination:** prefer the organization's internal certificate authority, with the issuing root trusted by every kiosk tablet and a server certificate whose subject alternative name contains the chosen FQDN. If no internal certificate path exists, decide whether an approved DNS-based certificate path is available. Do not use a browser warning bypass or a self-signed certificate that clients do not trust. Microsoft documents HTTPS certificate bindings for IIS in [IIS SSL setup](https://learn.microsoft.com/en-us/iis/manage/configuring-security/how-to-set-up-ssl-in-iis); the proxy product and certificate renewal process still need to be selected.
- **Proxy and ports:** use the existing approved Windows-compatible reverse proxy if present; otherwise select and install one during deployment. Terminate HTTPS at the proxy on the agreed client-facing port (normally 443), and proxy to Next.js on loopback port 3000. Do not assume port 80 or 443 is free. Configure HTTP-to-HTTPS redirect only if the chosen proxy and network policy allow it.
- **PIN login protection:** configure the proxy to rate-limit `POST /api/control-auth/login` and verify that repeated incorrect PIN attempts are throttled before exposing the kiosk to the LAN. Device control routes require the resulting short-lived PIN session.
- **Process supervision:** choose an approved Windows service wrapper/supervisor for two long-running processes: Next.js and the Cast sidecar. Run them as a dedicated, non-administrator service identity. Confirm restart-on-failure, startup ordering, working directories, log locations, and how updates roll back. Microsoft describes service accounts in [Service User Accounts](https://learn.microsoft.com/en-us/windows/win32/services/service-user-accounts).
- **Network placement:** place server01 on the same subnet as Cast devices if automatic discovery is required. Confirm the Wi-Fi access point forwards multicast and does not isolate clients. Do not expose the sidecar's port 8765 to kiosk clients or other networks.
- **CSV path:** choose either a local server01 copy or a read-only Windows file share. Confirm permissions using the actual service identity, not an interactive administrator session.

## First deployment steps

1. **Install and stage.** On server01, confirm Windows 10 patch level, available disk space, and restart policy. Install the supported Node.js runtime and Python 3.11+ from approved sources. Copy the reviewed app release and Cast bridge into stable local folders. Install dependencies from the lockfile and bridge `requirements.txt`; do not run `git pull` or dependency installation during service startup.
2. **Build and smoke-check locally.** From the app release folder, set the production environment and run `npm run build`. Start Next.js under the selected supervisor, bound to loopback at port 3000 (for example, `npm run start -- --hostname 127.0.0.1 --port 3000`). Start the Python bridge as a separate supervised process with `CAST_BRIDGE_TOKEN` set. Confirm the app responds locally and the bridge is listening only on loopback before configuring the proxy.
3. **Store secrets with restricted access.** Use a protected secret store if available. Otherwise, keep a configuration file outside the source and release folders, grant read access only to the service identity and Windows administrators, and have the supervisor load values into the process environment. Do not place secrets in command-line arguments or logs. Keep the Spotify and Electrolux encrypted token stores at stable writable paths outside releases, restrict their ACLs to the service identity/administrators, and back each up with its matching encryption key; changing a key makes that integration's stored tokens unreadable. Keep the Cast token at least 32 characters and identical for the app and sidecar. See `docs/electrolux.md` for the Electrolux variables and setup.
4. **Configure the CSV read path.** If the CSV is on another PC, share only its containing data folder and grant the app service identity read-only access at both share and file-system levels. Set `SPEED_HISTORY_CSV_PATH` to a UNC path such as `\\pc-name\share-name\speedtest-results.csv`, not a mapped drive letter or the other PC's `F:` path. A Windows service may not have an interactive user's mapped drives. Do not grant the app identity write/delete rights to the producer's CSV. Alternatively, have a scheduled transfer publish a local server01 copy, with the publisher writing and the app identity read-only. Confirm whether copying while the producer appends can create a partial CSV; if it can, arrange a completed snapshot/atomic publish with the CSV owner before relying on the endpoint.
5. **Configure the proxy and certificate.** Bind the selected proxy to the confirmed FQDN and trusted certificate. Forward only to `127.0.0.1:3000`; configure the app's external HTTPS origin where any integration requires an exact callback URL. Permit client access only from the home/kiosk LAN on the selected HTTPS port. Do not publish the site or bridge to the public internet as part of this runbook.
6. **Set Windows Firewall rules narrowly.** Allow the kiosk subnet to reach the proxy's HTTPS listener. Keep Next.js 3000 and bridge 8765 loopback-only. For Cast discovery, permit the required inbound/outbound multicast DNS traffic on UDP 5353 for the trusted LAN profile and verify the router/AP forwards it. Do not open broad inbound access or forward these ports from the internet.
7. **Verify from a kiosk client.** Open the chosen HTTPS FQDN and confirm there are no certificate warnings. Install the PWA and verify its icon/standalone launch. Check that a failed network navigation can show the offline shell while API calls still fail normally (the worker deliberately does not cache API results). Check `/api/speed-history` for the expected recent rows and confirm the app service identity cannot modify the CSV. If Cast is enabled, check `/api/cast/devices` and run one controlled play/pause test; if discovery fails, verify subnet, multicast forwarding, Windows Firewall, and access-point isolation before changing code.
8. **Record operations.** Record the deployed release, service identities, secret-file ACL owner (not values), chosen origin, certificate renewal owner/date, proxy ports, CSV UNC/local path, firewall scope, and rollback procedure in the team's approved operations record. Do not put credentials there.

## Values still unknown

The first-deploy session must establish: server01's actual Windows 10 edition/build and permissions; stable DNS FQDN and address reservation; certificate authority and renewal owner; reverse-proxy choice and listener availability; app and bridge service manager; kiosk/Cast subnet and multicast policy; whether the CSV producer is server01 or another PC; and which optional integrations/secrets are enabled. The steps above deliberately leave these unset until verified.
